Cairn / redfish kyanite · design notes

Design Note · Draft

A bare-metal Redfish interface for Cairn, generated from CSDL.

Two tracks evaluated for the Kyanite management-controller stack: a schema-driven, dead-code-eliminable Redfish HTTP server generated directly from DMTF CSDL, and a Protobuf-centric exploration that adds ConnectRPC endpoints while keeping a single source of truth. The constant constraint is running on a real BMC without bloating the binary.

Target architecture

One annotated schema, derived from CSDL, fans out to two transport surfaces and a single hardware provider layer. The ConnectRPC surface uses native Protobuf; the Redfish HTTP surface is generated as explicit, reflection-free handlers so unimplemented resources never reach the binary.

PART I

The Go Redfish server, generated from CSDL

A purpose-built generator turns the normative CSDL schema into idiomatic Go models, reflection-free marshalers, and per-resource route registration. No existing project does this: gofish is a client, the airship/Nordix libraries are OpenAPI-generated clients, and kubevirtbmc is a hand-written server subset scoped to KubeVirt VMs.

1.1 Schema source — CSDL, not OpenAPI

DSP8010 ships three functionally equivalent forms — CSDL (OData EDMX, the normative primary), JSON Schema, and OpenAPI YAML. CSDL retains the OData type, navigation, and annotation metadata that the OpenAPI projection flattens, and that metadata is exactly what drives correct emission.

  • Generate with a custom text/template pipeline, reusing DMTF Redfish-Tools for CSDL parsing logic.
  • Do not use stock swagger-codegen / openapi-generator — they choke on the bundle and emit non-idiomatic, bloated client code.
  • The DMTF C struct generator is the architectural precedent: schema → struct + JSON converter for resource-constrained (UEFI/EDK2) targets.

1.2 Dead-code elimination is two problems

Marshaling & reflection

encoding/json reflection forces type retention, pulls in reflect, and is the dominant size cost on TamaGo. Generate explicit MarshalJSON per type (and UnmarshalJSON only for writable resources). This is the single largest binary-size lever and removes reflect from the link graph.

Routing

The blow-up comes from a generated global route table / giant switch / init()-registered map covering every resource — all reachable, none eliminable. Instead emit one registration function per resource:

// generated, one per resource — nothing references it until you do
func RegisterSystems(mux *http.ServeMux, p SystemsProvider) { /* ... */ }

// cairn/main.go — only what this BMC actually serves links in
redfish.RegisterServiceRoot(mux, root)
redfish.RegisterSystems(mux, sysBackend)
redfish.RegisterChassis(mux, chassisBackend)
// Thermal, UpdateService, … never referenced → eliminated

Anti-pattern

Never emit RegisterAll() or init()-based auto-registration. Either re-anchors every handler to the reachable graph and defeats DCE. Registration must be explicit and opt-in.

1.3 Layering for real hardware

  • Generated models stay pure DTOs — no client pointer, unlike gofish's Entity embedding.
  • A provider interface per resource group fills/returns DTOs; hand-written backends read PMBus/I²C sensors, GPIO power control, flash.
  • Backend errors map to the standard Redfish message registry (DSP8011). Everything except the provider implementations is generable.

1.4 OData mechanics the generator must emit

  • /redfish/v1 ServiceRoot, $metadata (EDMX), and the odata service document.
  • @odata.id / @odata.type / @odata.context / @odata.etag injection.
  • Collection shape (Members, Members@odata.count) vs singleton.
  • Navigation links as references, not eager expansion; optional $expand / $select.
  • ETag / If-Match with sparse PATCH dispatch; standard error response body.
  • Emit a trimmed $metadata covering only registered types via go:embed.

1.5 Subset at the source via profiles

Drive generation from a DMTF Interoperability Profile (DSP8013) or an explicit allowlist, so unimplemented schemas (Thermal, UpdateService, …) are never generated. This addresses the unused-route concern before DCE even runs, and pins the surface to a declared conformance target.

1.6 Router & reusable inputs

  • Go 1.22+ http.ServeMux method+pattern matching, or a small static radix tree. No reflection-based web frameworks.
  • Remaining size drivers on TamaGo are TLS/crypto and the JSON layer — generated marshalers plus a profile-trimmed schema keep it minimal.
  • Reusable inputs: gofish as a struct/field reference (strip client semantics), Redfish-Tools for the CSDL parser, the C struct generator as the codegen template.
PART II

Protobuf exploration — ConnectRPC alongside HTTP

Cairn uses Protobuf internally, so a CSDL → Protobuf mapping that loses no information (unlike OpenAPI) is attractive: it yields ConnectRPC endpoints natively and could, in principle, serve REST via Connect Vanguard. The DMTF "Benchmarking gRPC for Redfish" study proved the encoding is feasible as a transport, but it was a throughput study, not a fidelity-preserving mapping — and fidelity is the hard part.

2.1 CSDL → proto is lossless only with custom options

proto3 cannot natively express several OData constructs. To avoid the loss OpenAPI introduces, carry them in custom proto options (extensions), not in field shapes:

  • Navigation vs contained references (both become message refs → distinction lives in an option).
  • Read/write permissions, required-on-create, immutable-after-create.
  • Abstract/derived type hierarchy and the @odata.type version string (proto has no inheritance → oneof + literal type field).
  • Enum member metadata (proto3 forces a zero UNSPECIFIED member with no Redfish analog).
  • Units / measurement annotations.

Use protovalidate (buf.validate) for CEL-expressible constraints (ranges, patterns, required, enum membership); push the rest into CSDL-fidelity options. The proto becomes a strict superset of CSDL.

2.2 The JSON wire format is where Vanguard bites

Vanguard transcodes via protojson and resolves schemas through protoregistry.GlobalFiles using protoreflect. That produces three problems against a strict Redfish target:

Redfish expectationprotojson behaviorStatus
Integers as JSON numbersint64/uint64 → JSON stringfails
Explicit null for known-but-unavailable (e.g. offline sensor)unset fields omitted; no null emittedfails
String enums, no sentinelrequires zero UNSPECIFIED; name casingfriction
Typed, open Oem extensionsStruct (loses typing) or Any (untranscodable without registered schema)lossy
@odata.id, Members@odata.countsolvable via json_name overrideok

Two further consequences

DCE conflict: protoreflect + the global descriptor registry retain every compiled descriptor, undermining the per-route, register-only-what-you-implement strategy from Part I. Validation cost: protovalidate evaluates CEL at runtime via cel-go (parser + checker + interpreter) — a large dependency with no static-codegen path, costly on a flash-constrained BMC.

2.3 Embedded build notes

  • vtprotobuf generates static Marshal/Unmarshal/Size (no reflection) → lean, fast, DCE-friendly, but binary only. Use it as the codec on the ConnectRPC path.
  • Keep buf.validate annotations in the schema for documentation and codegen, but for the BMC image generate static validators (PGV-style) or restrict validation to write/PATCH paths, and exclude cel-go.
  • Pin one Redfish release for proto generation; emit @odata.type version literals rather than encoding history.

2.4 Recommendation — one proto, two backends

Verdict

Make the annotated proto the single source of truth and run two codegen backends from it. Use ConnectRPC for native/internal clients; generate the spec-compliant HTTP surface with a dedicated Redfish-JSON codec — not protojson/Vanguard.

  • Native surface → connect-go + vtprotobuf codec. Clean fit for Cairn's internal Protobuf usage; Connect/gRPC for free.
  • Redfish HTTP surface → the Part I generator (per-resource MarshalJSON + explicit Register*), fed from the same proto+options model. This is the only path that gets numbers, explicit null, typed Oem, and polymorphism right while keeping the DCE and size properties.
  • Vanguard becomes viable only if strict spec-compliance on the REST side is not required (internal tooling that tolerates protojson quirks). Validate against the DMTF Service and Protocol validators before committing either way.

Cut list — what not to ship

  • swagger-codegen / openapi-generator on the schema bundle.
  • RegisterAll() or init() route auto-registration.
  • encoding/json reflection on hot model types.
  • protojson for the spec-compliant Redfish surface.
  • cel-go / runtime protovalidate in the BMC image.
  • OpenAPI YAML as the generation source (lossy vs CSDL).
